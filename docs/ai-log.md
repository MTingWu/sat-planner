# AI 協作與除錯紀錄

這份紀錄整理開發 sat-planner 過程中遇到的問題，以及和 AI 協作解決的經過。

協作方式：我負責提出問題、定義需求與做最後決策，AI 負責分析原因、提出方案與產出程式碼；所有修改都經過本機測試與實際部署驗證。每一則都記下問題是怎麼被發現的，以及我從中學到什麼。

---

## 第一階段：環境建置與 API 雛形

### 1. 空間資料庫與 Python 套件的嚴格度差異（GeoJSON 閉合問題）

* **情境**：在測試 API 邊界條件時，傳入了一個僅有 3 個點（未閉合）的不合法 GeoJSON 多邊形。
* **問題**：系統未如預期回傳 422 錯誤，反而觸發了 500 Internal Server Error。
* **原因分析**：Python 的 `shapely` 套件較寬容，自動閉合了多邊形使得 `is_valid` 檢查通過。但原始 JSON 傳入嚴格遵守規範的 PostGIS 時，觸發了 SQL `DataError`。
* **解法**：在 API 資料庫連線區塊加入 `try...except psycopg.Error`，當資料庫拒絕解析時，優雅地轉換並回傳 422 錯誤提示。
* **學到什麼**：同一份資料經過不同套件，檢查的嚴格程度可能不同，驗證不能只依賴其中一層。
* **後續**：這個寫法後來被發現抓得太寬，資料庫斷線時也會被誤報成「GeoJSON 不合法」，見第 12 則。重新實測時，在目前使用的 PostGIS 版本中，未閉合的多邊形可以正常解析，不合法的 GeoJSON 拋出的則是 `InternalError_`。當初的例外類別可能與版本有關，最終的修法以實測結果為準。

### 2. Docker 環境下的資料庫初始化

* **情境**：初次啟動 Docker Compose 時，發現 PostgreSQL 資料庫內沒有自動建立資料表。
* **原因分析**：原本將 schema 腳本建立在 `db/` 目錄，但官方 PostgreSQL 映像檔只會執行放在 `/docker-entrypoint-initdb.d/` 的腳本。
* **解法**：將檔案移動到正確的掛載路徑 `db/init/01_schema.sql`，並使用 `docker compose down -v` 清除舊的 Volume 後重新啟動，成功建表。
* **學到什麼**：初始化腳本只在 Volume 第一次建立時執行，之後新增的 SQL 檔要手動匯入，這也是後來 `02_regions.sql`、`03_weather_grid.sql` 的匯入方式。

### 3. QGIS 空間查詢工具誤區

* **情境**：嘗試在 QGIS 驗證自動入庫的資料筆數與時間。
* **問題**：將 SQL 語句貼在「數據源管理器」的搜尋列無法執行。
* **解法**：透過 AI 協作釐清，應使用「資料庫管理器（DB Manager）」的 SQL 視窗來執行包含 `GROUP BY` 的統計語法。
* **學到什麼**：用熟悉的 GIS 工具直接查資料庫，是驗證入庫結果最快的方式。

## 第二階段：日曆改版、部署與可靠性（2026 年 11 月）

### 4. 日曆說「拍到台灣」，地圖上卻畫不出來

* **情境**：我自己測試時發現。11/20 的日曆顯示 S1C 會拍到台灣，但在雲林嘉義框選範圍後，點 11/20 只畫出 S2B 的條帶。
* **問題**：同一天、同一顆衛星，日曆和地圖給出不同答案。
* **原因分析**：日曆和推薦表用的是兩套不同的「範圍」。日曆用一個寫死的矩形（119.3–122.1°E、21.8–25.4°N）判斷，包含大片海域；推薦表則用使用者框選的範圍。S1C 那趟實際上只掃過台灣東北角，碰到了矩形，卻沒碰到雲林。
* **解法**：把「台灣」改成真正的陸地範圍（見第 5 則），並讓日曆在使用者框選後改用框選範圍重新計算，總覽和明細從此用同一個標準。
* **學到什麼**：兩個畫面對同一件事給出不同答案時，先找它們的「定義」差在哪裡，而不是先懷疑資料。

### 5. 縣市界線不能直接當作「台灣」

* **情境**：AI 在處理內政部縣市界線時，檢查每個縣市的範圍後發現。
* **問題**：行政區劃上，高雄市包含東沙與南沙（範圍一路到北緯 10 度），宜蘭縣包含釣魚臺。
* **原因分析**：直接合併所有縣市當作「台灣」，一趟只掃過太平島的取像也會被算成拍到台灣。
* **解法**：先把每個縣市拆成獨立島塊，再依位置分成本島、近岸離島、金馬與遠洋，遠洋以明確規則逐條列出方便審查。「台灣」定義為本島加近岸離島，這個範圍由我拍板決定。同時把幾何簡化，頂點數從約 33 萬降到約 9 千。
* **學到什麼**：行政資料和空間直覺不一定一致，用之前要先看資料實際長什麼樣子。

### 6. 只掃到一角，算不算「拍到台灣」？

* **情境**：修完第 4 則後，資料顯示 11/20 那趟 S1C 只蓋到台灣約 1.5%（新北、宜蘭、基隆）。
* **問題**：AI 建議預設範圍設 10% 門檻，未達的標為「部分拍到」。我一開始反對，因為那趟確實拍到了台北，對關心台北的人來說是完整的機會。
* **原因分析**：這是「摘要層級」的取捨：日曆一格只能放一個狀態，只掃一角和斜切過半個台灣不該長得一樣。
* **解法**：討論後採用 10% 門檻，但在 tooltip 和明細直接顯示涵蓋的縣市，資訊不會遺失。
* **學到什麼**：AI 的建議不是照單全收，但反對時也要聽完理由。這次討論讓設計更清楚，而不是單純誰對誰錯。

### 7. 時間沒有帶時區

* **情境**：AI 審查前後端程式時發現。
* **問題**：後端把時間輸出成 `2026-11-20T18:00:00`，沒有時區，前端由瀏覽器自行解讀。
* **原因分析**：我在台灣測試完全正常，但面試官若用 UTC 時區的電腦打開，日期篩選就會錯位。另外 `recommend()` 會直接改寫傳入的資料，是隱藏的副作用。
* **解法**：在 API 層統一輸出帶 `+08:00` 的台灣時間，`recommend()` 不再修改輸入。
* **學到什麼**：「在我的電腦上正常」不代表正確，時區問題要在設計時就處理。

### 8. 部署後雲量預報一直取不到

* **情境**：我在正式網頁上看到「雲量預報暫時無法取得」，本機卻正常。
* **問題**：原本的程式把錯誤吞掉，看不到原因。
* **原因分析**：加上 log 後看到 Open-Meteo 回 429：「今日請求額度已用完」。我們一天只呼叫幾十次，原因是 Open-Meteo 依 IP 計算額度，而 Render 免費方案的對外 IP 由很多服務共用。我也查了本機的快取表，確認本機是真的有連上，排除了「本機只是剛好走快取」的可能。
* **解法**：改成由 GitHub Actions 定時預抓台灣周邊 152 個格點的雲量存進資料庫，API 只讀資料庫，使用者請求時完全不呼叫外部服務。
* **學到什麼**：錯誤不能吞掉，否則連問題是什麼都不知道。外部服務要移出請求路徑，並設計好失敗時怎麼降級。

### 9. GitHub Actions 時好時壞

* **情境**：我在 Actions 頁面看到排程連續失敗。
* **問題**：錯誤是 TLS 握手逾時。
* **原因分析**：關鍵線索是同一次執行裡，前兩批失敗、後兩批成功，代表不是被封鎖，而是連線時好時壞。
* **解法**：加上三層重試：連線失敗立即重試、每批失敗後依序等 10、30、60 秒再試、全部跑完後補跑一輪。只有連線問題、429、5xx 才重試，參數錯誤（400）重試也沒用，直接放棄。
* **學到什麼**：先看失敗的「模式」再決定怎麼修。全部失敗和部分失敗，原因和解法完全不同。

### 10. 排程根本沒有跑

* **情境**：`/healthz` 顯示雲量超過 12 小時沒更新，但最近一次執行明明是成功的。
* **問題**：我對照 Actions 的執行時間才發現，一天四次的排程有兩次被跳過，另外兩次延遲一到四小時。
* **原因分析**：GitHub 的免費排程在尖峰時段會延遲甚至跳過，整點最嚴重，因為很多人的排程都設在整點。
* **解法**：排程改到每小時的第 23 分，雲量改成每 3 小時抓一次，就算偶爾被跳過，12 小時內仍有多次機會成功。
* **學到什麼**：程式沒錯不代表系統正常，需要有東西監控「資料是否新鮮」，而不只是「程式有沒有報錯」。

### 11. 入庫解析出 0 筆時，會把資料刪光

* **情境**：另一個 AI 做程式碼審查時指出，我請目前協作的 AI 確認後，發現實際情況比審查說的更嚴重。
* **問題**：入庫流程在同一個交易中「記錄計畫檔、刪除未來的舊取像、寫入新取像」。如果 ESA 改了 KML 格式導致解析出 0 筆，程式不會報錯，交易正常 commit。
* **原因分析**：結果是舊取像被刪光，計畫檔的 SHA-256 也被記錄，隔天重跑時判斷成「已處理過」而跳過，資料空洞永久留著。
* **解法**：把解析移到交易之前，0 筆就直接報錯，資料庫完全不動；下載加上 `raise_for_status()`；每顆衛星分開處理，一顆失敗不影響其他。並寫了整合測試，確認 0 筆時資料庫筆數前後完全相同。
* **學到什麼**：交易只能保證「全部成功或全部失敗」，保護不了「成功地做了錯的事」。

### 12. 另一個 AI 的修法本身有 bug

* **情境**：同一份審查建議把第 1 則加上的 `except psycopg.Error` 改成抓 `DataError`。
* **問題**：原本的寫法抓得太寬，資料庫連不上時也會被誤報成「你的 GeoJSON 不合法」（422），這點審查說得對。但它提出的修法本身有問題。
* **原因分析**：實際把壞資料送進 PostGIS 測試後，拋出的是 `InternalError_`（SQLSTATE XX000），不是 `DataError`，照抄的話原本要抓的錯誤反而會漏掉。實測也發現連線池逾時 `PoolTimeout` 和查詢逾時 `QueryCanceled` 都是 `OperationalError` 的子類別，如果不分開處理，查詢逾時會被說成「資料庫無法使用」。
* **解法**：依實測結果分別處理：GeoJSON 被拒回 422、資料庫連不上回 503、查詢逾時回 503 並說明「查詢時間過長」。
* **學到什麼**：AI 的建議方向可能對，細節卻可能錯。會影響程式行為的建議，先實測再採用。第 1 則當初的修法也是在這時被重新檢視的。

### 13. S2B 從日曆上消失

* **情境**：新加的 `/healthz` 回報「有衛星的計畫已過期」，對照資料發現是 S2B。
* **問題**：入庫紀錄裡完全沒有 S2B 這一行。
* **原因分析**：`latest_plans()` 最後一行會默默丟掉「最新計畫已經結束」的衛星。ESA 網頁上 S2B 最新的計畫停在 11/23，程式沒留下任何紀錄，它就這樣從日曆消失了。
* **解法**：改成回傳「進行中」和「已結束」兩份清單，已結束的衛星會印出紀錄；ESA 任一頁面一份計畫都比對不到時直接報錯。`/healthz` 對剛結束 14 天內的衛星發出警告，超過 14 天則列為「已停止發布」，不再永久警告。隔天 ESA 發布了 S2B 的新計畫，證實只是延遲；同時也看到 S1A 的計畫早在 6 月就停止發布了。
* **學到什麼**：「默默過濾」比報錯更危險。另外，不要太早下結論：如果一看到計畫過期就判定退役，S2B 就會被誤判。

### 14. CI 其實沒有測到資料庫

* **情境**：程式碼審查指出，我把 `test.yml` 交給 AI 確認。
* **問題**：CI 雖然啟動了 PostGIS 容器，卻沒有建立任何資料表，唯一的 API 測試也在查詢資料庫之前就結束了。
* **解法**：CI 先依序匯入 `db/init/*.sql`，再跑測試；新增整合測試，種入假取像後實際呼叫 API，驗證覆蓋率、狀態、縣市、錯誤處理與逾時。測試加上 `-rs`，若因資料庫沒建好而被略過，紀錄裡一眼就看得到。
* **學到什麼**：「有測試」和「測試真的有測到東西」是兩回事。

### 15. 介面不直覺

* **情境**：我自己操作後的回饋。
* **問題**：日曆用小色點的「位置」代表衛星，要先背順序才看得懂，兩顆雷達衛星長得一模一樣；拖曳面板寬度的把手在右下角；看條帶要點兩次。
* **解法**：日曆改成直接寫衛星名稱的標籤；點日期就把當天所有條帶畫在地圖上；最上方加上「接下來的觀測機會」直接回答使用者的問題；改用拖曳面板邊緣調整寬度；加上冷啟動提示和首次造訪說明。視覺上刻意避開常見的 AI 模板風格，改用製圖慣例：雷達條帶用斜線網紋，日曆標籤和地圖條帶用同一套語言。
* **學到什麼**：開發者覺得合理的設計，使用者不一定看得懂，要實際操作才知道。

## 開發環境的小坑

* **WSL 找不到 `docker` 指令**：Docker Desktop 沒開，或沒有啟用 WSL 整合。
* **WSL 裡連不上外部網站，瀏覽器卻可以**：WSL 的網路斷了，在 PowerShell 執行 `wsl --shutdown` 後重開即可。
* **新開終端機跑測試出現 `KeyError: 'DATABASE_URL'`**：環境變數只在當前終端機有效，改用 `tests/conftest.py` 提供本機預設值。
* **Neon 的 pooled 連線不支援 `options` 參數**：查詢逾時改用每個交易開頭的 `SET LOCAL statement_timeout`。
* **從 Windows 複製檔案進 WSL 會多出 `*:Zone.Identifier`**：加進 `.gitignore`。
